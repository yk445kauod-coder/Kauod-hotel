# تصميم: تطبيق سطح المكتب (نسختين) — أوفلاين + أونلاين + إصلاح الـ API

التاريخ: 2026-11-11
الحالة: بانتظار موافقة المالك

## الهدف (ليه)

الفندق عايز التطبيق يشتغل من **exe** على أجهزة الاستقبال، **أوفلاين بالكامل وأونلاين**، من غير
ما يفتح الرابط كل مرة ومن غير تثبيت أي runtime. النسخة الحالية بتفتح `kaoud-hotel.pages.dev`
كل تشغيل → محتاجة نت دايمًا. المطلوب نسختين:

- **حديثة (Win10/11):** صغيرة (~5MB)، بتستخدم WebView2 الموجود أصلًا في النظام.
- **ويندوز 7:** Chromium مدمج جواه (Electron 22)، بدون أي تثبيت.

والاتنين لازم: **يفتحوا فورًا أوفلاين**، يقرأوا من كاش محلي، يسمحوا بكل الكتابات أوفلاين،
وتتزامن مع الـ Cloudflare API لما النت يرجع.

## الوضع الحالي (اللي موجود فعلًا)

- **الويب** فيه بالفعل طبقة أوفلاين كاملة: outbox لكل الكتابات (`outbox.ts`)، طابور فواتير
  أوفلاين بأرقام محجوزة (`offline.ts`)، كاش قراءة (`cache.ts` + `useCachedList.ts`)،
  وService Worker (`sw.js`). **الويب مش محتاج تعديل منطقي كبير.**
- **الـ API** (Worker + Hono + D1) مصادقته **بالكوكيز فقط**: `kaoud_session` (HttpOnly) +
  `kaoud_csrf`. `CORS` مسموح لأصل واحد بس (`APP_ORIGIN = https://kaoud-hotel.pages.dev`).
- **تطبيق الديسكتوب القديم** (Go/walk) بيستخدم كوكي جار — منفصل تمامًا عن ده.

## المشكلة (اللي بنسميه «الباج»)

1. **الـ exe بيفتح الرابط** بدل ما يحزم ملفات التطبيق → محتاج نت كل تشغيل.
2. **الـ API بيرفض أي أصل غير `pages.dev`** → الديسكتوب (أصله `tauri://localhost` أو مخصّص) مرفوض.
3. **الكوكيز مرفوضة cross-origin** من نافذة الديسكتوب → مفيش جلسة.
4. **مفيش «جلسة أوفلاين»**: عند الفتح بينادي `/api/me`؛ لو فشل → شاشة دخول → مفيش أوفلاين.

## الأهداف

- exe يفتح فورًا أوفلاين، ويقرأ آخر بيانات متزامنة، ويكتب (فواتير/دفعات/غرف/نزلاء/حجوزات).
- مزامنة تلقائية عند رجوع النت (نفس منطق الـ outbox الموجود).
- نسختان: حديثة (WebView2) + Win7 (Chromium مدمج).
- **الويب يفضل شغال زي ما هو** (كوكيز)، والديسكتوب ياخد مسار مصادقة مستقل.
- بدون تثبيت أي runtime في النسخة الحديثة (WebView2 موجود في Win10/11).

## غير الأهداف

- إعادة كتابة الواجهة. نفس `apps/web` تتحزم كما هي.
- تغيير منطق الأوفلاين أو الترقيم (موجود وشغّال).
- مزامنة CRDT متعدد الماستر (الخادم مرجع واحد).

## مضاد-الأهداف (فشل)

- الويب يتكسر أمنيًا (تسريب توكن لـ XSS).
- رقم فاتورة يتكرر بين جهازين.
- كتابات أوفلاين تختفي بصمت.
- التطبيق يحتاج نت للفتح.

## الطرق المتاحة (how)

**أ) الـ API يقبل `Bearer` للديسكتوب + كوكيز للويب، وحزم `dist` محليًا. (موصى به)**
- الـ exe يحزم `apps/web/dist` → يفتح فورًا.
- الديسكتوب يسجّل الدخول → ياخد **توكن جلسة** يخزّنه → يستخدمه في كل الطلبات.
- الـ API يقبل التوكن جنب الكوكي؛ CORS يسمح بأصول الديسكتوب.
- لا كوكيز cross-origin → مصادقة نظيفة ومستقرة.
- التعديلات: `http.ts`, `auth-middleware.ts`, `routes/auth.ts` + `api.ts` + شل الديسكتوب.

**ب) سيرفر محلي جوه الـ exe يعمل بروكسي للـ `/api` للـ Worker → نفضل على الكوكيز.**
- نفس النتيجة، بس كوكيز cross-origin هشّة + عملية إضافية (فتح بورت محلي) + تعقيد أمني.

**ج) نكتفي بالـ Service Worker.** مرفوض: بيخزّن القشرة بس، والجلسة لسه بتفشل أوفلاين.

## القرار

**الطريقة (أ).** الأضمن أمنيًا (الويب يفضل HttpOnly cookie، والديسكتوب توكن صريح)، والأبسط
تشغيليًا (مفيش بورت محلي)، وبيحقق «أوفلاين + أونلاين» للنسختين.

## المكوّنات

### 1) الـ API (Worker) — تعديلات

- **`auth-middleware.ts`:** قراءة التوكن من `Authorization: Bearer <token>` **أو** كوكي
  `kaoud_session`. لو Bearer → **تخطّي CSRF** (التوكن مش بيئي، مش محتاج double-submit).
  لو كوكي → CSRF زي ما هو. باقي المنطق (انتهاء/تعطيل/RLS) واحد.
- **`http.ts`:**
  - `Access-Control-Allow-Headers` += `Authorization`.
  - `allowedOrigins`: تضم أصول الديسكتوب (`http://tauri.localhost`، `app://kaoud`،
    و`file://` مش ممكن → نستخدم scheme مخصّص في Electron). تُضاف من `APP_ORIGIN_EXTRA`
    (بدون تعديل كود) أو متغيّر جديد `DESKTOP_ORIGINS`.
- **`routes/auth.ts`:**
  - `POST /api/auth/login`: لو الطلب جاي من الديسكتوب (هيدر `X-Client: desktop`) →
    نرجّع `token` (نص التوكن) في الرد **كمان**. الويب مايستلموش (ياخد كوكي بس) →
    ما نضعّفش أمان الويب (مفيش تسريب توكن لـ XSS في المتصفح).
  - `POST /api/auth/logout`: يعمل بالتوكن (Bearer) أو الكوكي.
  - `GET /api/me`: يعمل بالتوكن.
- **إضافي (بسيط):** `POST /api/auth/token` — يبدّل جلسة كوكي قائمة بتوكن صريح (اختياري).

### 2) الويب — تعديلات صغيرة (متوافقة للخلف)

- **`api.ts`:** لو فيه توكن مخزّن (بيئة الديسكتوب) → `Authorization: Bearer` وبدون
  `credentials`/CSRF. غير كده → السلوك الحالي (كوكيز). كشف البيئة: وجود
  `window.__KAOUD_DESKTOP__` أو توكن في `localStorage`.
- **جلسة أوفلاين (`App.tsx` + `offline.ts`):** تخزين آخر `user` + `settings` معروفين.
  عند الفتح: جرّب `/api/me`؛ لو فشل بسبب الشبكة → استخدم الجلسة المخزّنة وافتح التطبيق
  في وضع أوفلاين بدل شاشة الدخول. (شاشة الدخول تظهر فقط لو مفيش جلسة مخزّنة أو رجع 401.)
- **مؤشر «بيانات آخر اتصال»** موجود بالفعل — نستخدمه كما هو.

### 3) شل الديسكتوب (نسختان)

نبني **شلّين صغيرين داخل الريبو** بنفس محرّكي PakePlus/PakePlus-Win7 (تحكّم كامل + بناء CI):

- **`apps/shell-modern/`** — **Tauri v2** (Rust) → WebView2.
  - يحزم `apps/web/dist` كـ `frontendDist`.
  - الحجم النهائي ~5MB (بدون WebView2 لأنه موجود في Win10/11).
- **`apps/shell-win7/`** — **Electron 22.3.27** (آخر نسخة تدعم Win7) → Chromium مدمج.
  - يحمّل `apps/web/dist` محليًا عبر scheme مخصّص `app://kaoud` (مش `file://`) عشان
    الـ localStorage/IndexedDB تشتغل والـ CORS يكون محدد.
  - الحجم ~150MB (الكروميوم جواه) — مقبول لأنه بدون أي تثبيت على Win7.
- **في الاتنين:**
  - `VITE_API_BASE` = `https://kaoud-hotel-api.yk445kauod.workers.dev` (مطلق، لأن الأصل محلي).
  - عند أول تشغيل أونلاين: دخول → تخزين التوكن + الجلسة.
  - بعد كده: فتح فوري أوفلاين من الكاش + outbox.

### 4) البناء والنشر

- **GitHub Actions `windows-latest`** (الموجود فعلًا في `.github/workflows/desktop.yml`
  نضيف له workflow جديد `.github/workflows/shell.yml`):
  1. `npm ci && npm run build -w @kaoud/web` → `apps/web/dist`.
  2. بناء `shell-modern` (Tauri) و`shell-win7` (Electron).
  3. رفع الـ exe كـ artifacts + نسخها إلى `downloads/`.
- المخرجات: `downloads/KaoudHotel-Modern.exe` و`downloads/KaoudHotel-Win7.exe`.

## القرارات التقنية (اختياراتي)

1. **مصادقة مزدوجة** (كوكي + Bearer) بدل استبدال الكوكي → الويب مايتغيّرش أمنيًا.
2. **التوكن يترجّع فقط لعميل الديسكتوب** (`X-Client: desktop`) → مفيش تسريب للمتصفح.
3. **CSRF يتخطّى للـ Bearer فقط** → صحيح أمنيًا (التوكن مش بيئي).
4. **شلّان داخل الريبو** (Tauri + Electron) بدل الاعتماد على PakePlus كأداة GUI →
   يخلي البناء قابل للتكرار في CI، ويتحكم في حزم `dist` والتوكن.
5. **Electron scheme مخصّص** `app://kaoud` بدل `file://` → تخزين + CORS سليم.

## الأمان

- الويب: HttpOnly cookie + CSRF كما هو (بدون تغيير).
- الديسكتوب: توكن في تخزين محلي؛ يُفضّل تشفيره عبر DPAPI (Windows) في النسخة النهائية.
- نفس التحقّق من الصلاحيات (RLS) على الخادم — الأوفلاين يقرأ بس بيانات المستخدم المتزامنة.
- مفيش أي حذف بيانات حقيقي.

## النشر (إلزامي — جزء من التسليم)

1. تعديل الـ Worker (auth + CORS) واختبار حيّ: `/api/health` = 200، وكتابة بدون مصادقة = 401،
   وتسجيل دخول بـ `X-Client: desktop` يرجّع `token`.
2. `npm run deploy:api` (Worker).
3. `npm run build -w @kaoud/web` + نشر الصفحات (للويب).
4. بناء النسختين عبر GitHub Actions → artifacts + `downloads/`.
5. فحص: الويب لسه بيدخل بالكوكيز؛ الديسكتوب يدخل ويشتغل أوفلاين.

## اللي فاضل للمنفّذ

- تفاصيل scheme الـ Electron وإعداد Tauri (CSP، أذونات).
- تخزين التوكن على الديسكتوب (DPAPI أو تخزين محلي بسيط في v1).
- نصوص شاشة «تشغيل أوفلاين» ومتى تظهر.
- أيقونات الـ exe (من `apps/web/public/icon-512.png`).

## المخاطر

- **Tauri build على CI**: يحتاج Rust + WebView2 SDK على `windows-latest` — متاح.
- **Electron 22 قديم**: مقبول (آخر نسخة تدعم Win7)، لكن مفيش تحديثات أمنية — نحدّد الاستخدام.
- **CORS/أصل الديسكتوب**: لازم التأكد من قيمة أصل Tauri على ويندوز (`http://tauri.localhost`)
  وأصل Electron المخصّص — تُضاف لـ `APP_ORIGIN_EXTRA`.
