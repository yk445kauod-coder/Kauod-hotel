# تصميم: وضع الأوفلاين الكامل (كل الكتابات + قراءة من كاش) + حماية الخروج + مؤشر المزامنة

التاريخ: 2026-11-10
الحالة: بانتظار موافقة المالك

## الهدف (ليه)

الفندق بيفصل عنه النت والكهرباء. لازم **كل شغل الاستقبال** يشتغل أوفلاين ويرجع يتزامن لوحده لما
النت ييجي — مش إنشاء الفواتير بس. والمستخدم لازم يفهم بوضوح: إيه اللي مستني الرفع، وإمتى بيتزامن،
وممنوع يقفل التطبيق/يخرج ويسيب شغل غير مرفوع.

## النطاق

- **الكتابة أوفلاين:** كل عمليات الكتابة (فواتير، دفعات، قفل/فتح/إلغاء، غرف، نزلاء، حجوزات).
- **القراءة أوفلاين:** آخر نسخة سليمة من قوائم الفواتير/الغرف/النزلاء/الحجوزات تتحفظ وتُعرض أوفلاين
  مع شارة «بيانات آخر اتصال».
- **مستثنى (يتطلب نت عن قصد، بيلفت نظر المستخدم):** إدارة المستخدمين (صلاحيات/أمان)، الإعدادات
  والهوية، أرقام الفواتير (تسلسل مركزي)، رفع ETA، تغيير كلمة السر، والـ import/backup. هذه
  عمليات نادرة وإدارية، وتنفيذها أوفلاين خطر (تعارض أو مخاطرة أمنية).

## الطريقة المختارة

**Outbox موحّد + كاش قراءة (الطريقة ج).**
- كل كتابة تدخل «صندوق صادر» واحد في IndexedDB، تتنفّذ فورًا على الواجهة (optimistic)، وتُرفع
  بالترتيب لما النت يرجع. الخادم يتعامل مع أي عملية مكرّرة بنفس المفتاح مرة واحدة فقط.
- القراءات تُخزَّن (آخر رد ناجح) وتُخدَم أوفلاين.

## القرارات التقنية

1. **الخادم يقبل id من العميل.** الموبايل يولّد id بنفس صيغة الخادم (`room_`/`gst_`/`res_`/`pay_`…)
   عشان يقدر يشاور على سجلات أنشأها أوفلاين. لو الـ id موجود مسبقًا → العملية تُعتبر مكرّرة
   (idempotent) وتُرجع نفس النتيجة، مش خطأ.
2. **جدول idempotency عام:** `op_keys (tenant_id, op_key PRIMARY KEY, result_json, created_at)`.
   كل عملية كتابة تحمل هيدر `X-Op-Key` (uuid من العميل). أول تنفيذ يخزّن النتيجة؛ أي إعادة ترسل
   نفس الرد بدون تنفيذ تاني. (الفواتير عندها بالفعل `op_id` — هنعمّم نفس الفكرة على مستوى الوسيط.)
3. **ترتيب الرفع:** الـ outbox يُرفع FIFO حسب وقت الإنشاء، عشان الحجز اللي بيشاور على نزيل يرفع
   بعد النزيل. لو عملية فشلت بخطأ منطقي (4xx غير 401/409) تتعلّم «مرفوضة» وتُعرض للمستخدم بدل
   ما توقف الطابور.
4. **دمج القراءة أوفلاين:** القائمة المعروضة = (كاش آخر رد) + (العمليات المعلّقة مطبَّقة فوقه محليًا).
   يعني لو عملت نزيل أوفلاين، تلاقيه في القائمة فورًا حتى قبل الرفع.
5. **العمليات المعلّقة/المرفوضة** تتعرض في شاشة «العمليات المعلّقة» (مع «أعد المحاولة» و«احذف
   المرفوضة»).

## حماية الخروج

عند الضغط على «خروج»:
- لو مفيش عمليات معلّقة → يخرج عادي.
- لو فيه → يحاول يزامن؛ نجح (المعلّق = 0) → يخرج.
- لسه معلّق أو أوفلاين → **يُمنع الخروج** برسالة: «لازم ترفع العمليات المعلّقة الأول (N)».

## مؤشر المزامنة

- **داخل الجزيرة الديناميكية:** سبينر + عدّاد «N بانتظار الرفع» أثناء المزامنة.
- **شريط رفيع أعلى الشاشة** يظهر أثناء المزامنة فقط (يتشاف حتى والجزيرة مطوية).
- **توست** عند الانتهاء: «تم رفع N عملية».
- شارة صغيرة «بيانات آخر اتصال» على القوائم لما تكون معروضة من الكاش.

## النشر (إلزامي — جزء من التسليم)

1. **Migration جديدة** `0005_op_keys.sql` → تُطبّق على D1 البعيد (`--remote`)، مع فحص الـ ledger
   قبلها عشان نتجنب drift.
2. `npm run deploy:api` (worker).
3. `npm run deploy:web` (vite build → pages deploy).
4. **فحص حيّ:** `/api/health` = 200، ونقاط الكتابة الجديدة ترد 401 بدون مصادقة.
5. **تأكيد إن مفيش حذف** لأي بيانات حقيقية.

## اللي فاضل للمنفّذ

- صيغة `X-Op-Key` والنتيجة المخزّنة لكل نوع عملية.
- تفاصيل تخزين الكاش (مفاتيح، إبطال بعد كل كتابة ناجحة).
- الشكل النهائي للتوست/الشريط.

## غير الأهداف

- حل تعارضات متعدد الأجهزة معقّد (مفيش: الخادم مرجع واحد، والـ idempotency بيمنع التكرار).
- كتابة أوفلاين للعمليات الإدارية/الأمنية (المذكورة فوق).
- إعادة بناء قاعدة محلية كاملة (Mirror) — مرفوضة لتعقيدها.
